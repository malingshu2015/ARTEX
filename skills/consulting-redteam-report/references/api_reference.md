# 报告章节与图表细则

此文档是 consulting-redteam-report 的延伸规范。只在需要生成整项报告、复杂图表或交付检查时加载。

## 整项报告的数据字段

| 模块 | 推荐字段 | 来源与约束 |
| --- | --- | --- |
| 封面 | 项目名称、报告类型、版本、生成日期、密级 | 当前任务元数据；缺项写“未提供” |
| 执行摘要 | 总发现数、严重性分布、受影响资产、复测概况 | 从去重后的当前任务发现和资产计算 |
| 范围与方法 | 目标、排除项、窗口、方法、限制 | 任务授权与执行记录 |
| 攻击链 | 阶段、前置条件、验证结果、证据编号 | 已验证执行轨迹；推断步骤须显式标示 |
| 拓扑与资产 | 资产、类别、边界、已验证关系 | 任务资产及证据；不得仅凭命名推断连接 |
| 风险矩阵 | 可能性、影响、风险等级、评定依据 | 采用任务定义的评分规则并说明口径 |
| 漏洞统计 | 严重性、类别/根因、资产去重口径 | 以报告纳入的发现为总体，避免重复计数 |
| 单项发现 | 编号、标题、等级、资产、影响、成因、证据、修复、复测 | 漏洞记录、原始证据和复测记录 |
| 路线图 | 阶段、动作、依赖、优先级、验收条件 | 从修复建议归纳；不虚构负责人和日期 |

## 漏洞发现写作模板

每项漏洞建议沿用以下顺序，标题可按产品实际字段稍作调整：

1. 标题与元数据：漏洞编号、名称、严重性、状态、受影响资产、发现/复测日期。
2. 执行摘要：说明问题、攻击前提和影响范围。
3. 风险与影响：描述机密性、完整性、可用性或业务流程影响；区分直接验证结果和潜在后果。
4. 技术成因：指出配置、代码或流程的根因；资料不足时明确待确认。
5. 复现与证据：前置条件、编号步骤、实际结果、证据 ID。只放最小必要且已脱敏的请求/响应片段。
6. 修复建议：给出直接修复、纵深防御和优先级；建议需对应已识别根因。
7. 复测标准：写出修复后预期结果及仍需验证的边界。

## 图表数据契约

图表数据应能由报告表格或任务记录复算。注明统计口径，必要时将数值表放在图旁，避免图表成为无法审计的黑盒。

- KPI 卡片：使用 3–5 项，每项含指标名、数值和统计范围。不要重复展示近似指标。
- 攻击链流程：显示阶段、动作、结果、证据 ID。未验证路径不得画成已发生的成功链。
- 网络拓扑：用不同形状区分入口、边界、应用、主机、身份系统和数据资产。实线代表有证据的关系，虚线代表待验证推断，并在图例中说明。
- 风险矩阵：标明可能性、影响等级和评分口径；每个矩阵项应能回链到漏洞编号。
- 严重性与归因统计：显示实际数量和标签。只有样本足够时才呈现 CWE、根因或资产类别；小样本优先用表格。
- 整改路线图：按紧急修复、短期治理、中期改进分层，列出动作、依赖和验收条件。没有明确日期时不用具体时间轴。

## 交付排版

- 使用单一主标题层级和一致的章节编号；标题、表头、图题和正文有清楚层次。
- 标题使用深蓝，绿色用于细分隔线、章节标记和图表重点，正文使用高对比度蓝灰/深灰。
- 重点结论用简短摘要框突出，避免大面积实底色和重复强调。
- 表格每列含义明确；跨页重复表头；单位和日期格式全篇统一。
- 图片标注编号、标题、来源/统计口径和替代文本。若渲染器无法可靠显示图片，使用可读表格代替。
- 最终导出后检查目录、分页、页眉页脚、表格拆分、图表清晰度和敏感信息遮蔽。

## 事实与修订检查

- 每个统计指标注明筛选条件和去重方式，严重性总和应与发现总数一致。
- 风险图、摘要卡片、统计表和正文采用同一份数据快照。
- 对每个结论执行“来源—推理—结论”检查，尤其审查影响范围和攻击链跨越。
- 检查凭据、Cookie、令牌、个人信息、内部地址和不必要的原始流量是否被遮蔽。
- 占位文本应替换、删除或明确标为未提供，不能将模板示例当成项目事实。
